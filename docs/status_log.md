## 3. 課題 — P1: 実運用の前提が崩れている

実データを入れると成立しないもの。設計判断が先に要り、コードだけでは閉じない。

### 3-1. 卸側の医院コードの対応表が無い

現状は「卸CSVの医院コード = クリニックID(UUID)」として扱っている。実際の卸が自社の医院コード体系ではなくUUIDを送ってくることはないため、**このままでは医院別単価が1件も紐付かない**。

- 変換は[facility_resolver.go](../../clinic-inventory-csv-functions/internal/infrastructure/distributorcsvingestion/facility_resolver.go)1か所に閉じてあるので、対応表さえ決まれば差し替えは局所で済む
- 決めるには卸から実物のCSVと医院コード体系をもらう必要がある

### 3-2. 契約(クリニック×卸業者)が未実装

「契約はクリニック×卸業者の単位」と決めているのに、契約を表すデータも画面も無い。そのため**取引の無い卸・商品まで選べる**。卸ポータル側の閲覧範囲も絞れていない。詳細は[requirements.md 9章](requirements.md#9-未確定事項次に詰める)。

## 4. 課題 — P2: 業務が回らない / データが壊れる

### 4-1. 発注CSVが卸ごとのフォーマットに対応していない

日本語ヘッダ9列・UTF-8固定で、全卸に同じCSVを送っている([purchase_order_csv_uploader.go](../backend/internal/infrastructure/procurement/purchase_order_csv_uploader.go))。卸が読めなければ発注が通らない。

- `oroshi-a`は商品マスタをShift_JISで送ってくる。この卸は発注CSVもShift_JISを要求する可能性が高く、今のままでは文字化けする
- **入り側に鏡像となる正解がある**。取り込みの`ParserRegistry`(卸コード → パーサ)と同じ形で、卸コード → 発注CSVエンコーダの対応表を作ればよい。設計を新しく考える必要はない

### 4-2. 廃盤になった卸商品が発注できてしまう

廃盤チェックはクリニック商品の**登録時のみ**。登録後に卸が廃盤にしても、カート追加・発注確定のどちらでも検証していない。商品マスタCSVの取り込みで`discontinued`が自動更新されるようになったため、この状態は実際に発生する。止める場所と強さが未決([requirements.md 9章](requirements.md#9-未確定事項次に詰める))。

## 5. 課題 — P3: 精度・鮮度の問題

| 項目 | 内容 |
|---|---|
| 単価が実勢に追随しない | 医院別単価は**登録時点の値をコピー**する設計のため、卸が単価を変えても既存のクリニック商品は古いまま。自動追随させるか人が判断するか未決 |
| CSVから消えた商品の扱い | 現状は放置(廃盤にしない)。全件洗い替えの卸に対して自動廃盤にするかは未決 |
| 受注確定CSVの受け皿が無い | 納入単価・確定数量・欠品を受け取れない。分納の有無・完了判定が未確定。論点は`clinic-inventory-csv-functions`の`docs/order-acknowledgement-import.md` |
| 在庫コンテキストが未実装 | ドメインルール(FEFO・ロット・使用期限)は策定済みだがコードが無い |

## 6. 次の予定

**手を動かせるのは4-1から。** P1の2件は卸からの実データ・業務確認が要るため、着手できるまでは調査待ちになる。

1. **発注CSVの卸別アダプタ化**(4-1) — `ParserRegistry`の鏡像を作る。設計が決まっており実装コストが読める
2. **廃盤商品の発注ブロック**(4-2) — 止める場所を決めればコードだけで完結する
3. 卸側の医院コード体系の確認(3-1) — 卸への確認事項。**確認が取れ次第これが最優先に繰り上がる**
4. 契約テーブルの要否判断(3-2)
5. 受注確定CSVの実装(5章)
