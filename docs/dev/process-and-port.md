# プロセスとポート — 開発サーバが「止まらない」「起動しない」の読み解き方

`go run` や `npm run dev` で起動した開発サーバが、止めたはずなのに動いている・起動しようとすると
「address already in use」と言われる、といった場面を自力で切り分けるためのノート。

2026-08-15 に実際に起きた出来事を題材にする。

最終更新: 2026-08-15

---

## 1. 実際に起きたこと

バックエンドを止めて起動し直そうとして、こうなった。

```
$ ./run.sh
clinic-inventory api listening on :8080
server stopped: listen tcp :8080: bind: address already in use
```

止めたはずなのに、8080番を誰かが使っている。調べると、こういう状態だった。

```
$ lsof -nP -iTCP:8080 -sTCP:LISTEN
COMMAND   PID  USER   FD   TYPE  NAME
api     95991 apple    7u  IPv6  TCP *:8080 (LISTEN)

$ ps -p 95991 -o pid,ppid,lstart,command=
  PID  PPID STARTED
95991     1 土  8/15 08:34:48   /Users/apple/Library/Caches/go-build/8e/....../api
```

**PPID(親のPID)が 1 になっている**のが手がかり。ここから何が起きたか読み解ける。

---

## 2. プロセスと親子関係

プロセスとは「実行中のプログラム1つ」。それぞれに**PID**（プロセスID）という番号が付く。

プロセスは別のプロセスから起動される。起動した側が**親**、された側が**子**で、
子は自分の**PPID**（親のPID）を覚えている。

```
zsh (ターミナル)
 └─ go run ./cmd/api      ← 親
     └─ api               ← 子（実際にHTTPを待ち受けているのはこっち）
```

### なぜ `go run` は2つのプロセスになるのか

`go run` は「コンパイルしてから実行する」コマンドで、この2段階が別プロセスになる。

1. `go run` 自身がソースをビルドし、実行ファイルを**キャッシュ**（`~/Library/Caches/go-build/...`）に作る
2. その実行ファイルを**子プロセスとして起動**する

だから `ps` で見ると `go run ./cmd/api` と `.../go-build/..../api` の2行が出る。
**ポートを掴んでいるのは子のほう**で、親はそれを待っているだけ。

C#の `dotnet run` も同様に、ビルドしてから `MyApp.dll` を別プロセスで動かす。
`npm run dev` も、npm が親、実際のViteのnodeプロセスが子。

### 孤児プロセス（今回の原因）

親だけを終了させると、子は道連れにならず**生き残る**。親を失った子は、OSによって
PID 1（macOSでは `launchd`、Linuxでは `init`/`systemd`）の子として引き取られる。
これが**孤児プロセス**で、`PPID = 1` はその印。

今回は、プロセスを名前で探して終了させる `pkill -f "cmd/api"` を使ったのが原因だった。

| プロセス | コマンド行 | `cmd/api` を含むか |
|---|---|---|
| 親 | `go run ./cmd/api` | 含む → **終了した** |
| 子 | `/Users/apple/Library/Caches/go-build/…/api` | 含まない → **生き残った** |

パターンにマッチした親だけが死に、ポートを持っている子が残った。
結果、「プロセスは無いように見えるのに8080が空かない」状態になった。

> `Ctrl+C` なら、ターミナルが**プロセスグループ全体**に終了シグナルを送るので親子ともに止まる。
> 名前で狙い撃ちする `pkill` は、この「まとめて」が効かない点に注意する。

---

## 3. ポートの割り当て

- ポート（8080、5173 など）は、プロセスが `listen` することで**OSから借りる**もの。
- **同じポートを2つのプロセスが同時に listen することはできない**。だから2つ目は
  `address already in use` で起動に失敗する。
- プロセスが終了すれば、OSが自動的にポートを解放する。ポートは「ファイルのように残る」ものではなく、
  **掴んでいるプロセスが居るかどうか**が全て。

このプロジェクトのポート:

| ポート | 何が使うか |
|---|---|
| 8080 | バックエンド（`go run ./cmd/api`。`PORT` 環境変数で変更可） |
| 5173 | クリニック向けフロント（`npm run dev`） |
| 5174 | 卸ポータル（`npm run dev`） |
| 5432 | PostgreSQL |

### 「止めたのにすぐ再起動できない」場合

まれに、プロセスは終了しているのに数十秒だけポートが空かないことがある（TCPの`TIME_WAIT`）。
`lsof` に `LISTEN` が出ないのに bind できないときはこれを疑い、少し待つ。
今回のように `LISTEN` が出ている場合は、**生きているプロセスが居る**ので待っても解決しない。

## 4. 調べ方（コマンド）

### 誰がそのポートを使っているか

```bash
lsof -nP -iTCP:8080 -sTCP:LISTEN
```

- `-n` 名前解決しない（速い）／`-P` ポート番号を数字のまま出す
- `-sTCP:LISTEN` 待ち受けているものだけに絞る（接続中のクライアントは除く）

### そのプロセスは何者か

```bash
ps -p 95991 -o pid,ppid,lstart,command=
```

`ppid` で親を、`lstart` で**いつ起動したか**を確認する。起動時刻は特に重要で、
「コードを直したのに反映されない」ときは、**修正前に起動した古いプロセスが生きている**ことが多い。

### 関連するプロセスを一覧する

```bash
ps -eo pid,ppid,lstart,command | grep -E "cmd/api|exe/api" | grep -v grep
```

親子の両方が出るか確認する。片方しか出ないなら、今回のような取り残しを疑う。

### 止める

```bash
kill 95991          # 行儀よく終了させる（推奨）
kill -9 95991       # 応答しない場合の最終手段。後始末をせず強制終了する
pkill -f "cmd/api"  # コマンド行がパターンに一致するものを全部
```

**確実なのは「ポートから辿って kill する」順序**。名前で消すより取りこぼしがない。

```bash
kill $(lsof -t -nP -iTCP:8080 -sTCP:LISTEN)
```

---

## 5. 症状から原因を引く

| 症状 | 疑うこと | 確認 |
|---|---|---|
| `address already in use` | 古いプロセスが生きている（孤児を含む） | `lsof -nP -iTCP:8080 -sTCP:LISTEN` |
| コードを直したのに挙動が変わらない | 修正前に起動したプロセスがまだ動いている | `ps -o lstart` で起動時刻を見る |
| `Ctrl+C` したのにブラウザから繋がる | 親だけ止まって子が残った | `PPID` が 1 になっていないか |
| ターミナルを閉じたらAPIも落ちた | フォアグラウンド実行だった | バックグラウンド実行にするか、別ターミナルで動かす |
| DBの列を足したら `cached plan must not change result type` | 起動中のプロセスが古いスキーマの実行計画を持っている | 再起動する（S3等とは無関係のDB側の話） |

---

## 6. このプロジェクトでの安全な再起動手順

```bash
# 1. 誰が8080を使っているか確認する
lsof -nP -iTCP:8080 -sTCP:LISTEN

# 2. ポートを掴んでいるプロセスを止める（親子とも確実に消える）
kill $(lsof -t -nP -iTCP:8080 -sTCP:LISTEN)

# 3. 空いたことを確認してから起動する
lsof -nP -iTCP:8080 -sTCP:LISTEN   # 何も出なければOK
cd backend && ./run.sh
```

フロントエンド（5173 / 5174）も同じ手順で、ポート番号だけ読み替える。
