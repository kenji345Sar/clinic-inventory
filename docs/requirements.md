# クリニック医薬品在庫管理システム — 要件定義（v0）

このドキュメントは要件のたたき台。これ1枚で「何のために・誰が・何をするシステムか」が分かるように書き、理由や細部は各ドキュメントへリンクする。

---

## 背景と目的

医科・歯科・獣医クリニックにおける医薬品（医療備品）の在庫管理を効率化する。
複数クリニックへの展開を前提とし、法人・グループ単位の管理にも対応する。
**クリニック向けサイト**と**卸業者向けポータル**の2つのフロントエンドを持つ。

**対象外**: 患者への処方履歴の管理（電子カルテ的な機能）は対象外。在庫消費の記録は「いつ・どの商品を・何個」までとし、患者情報とは紐づけない（詳細は[決定事項](#決定事項)）。

---

## 利用者と組織

| アクター | サイト | 主な操作 |
|---|---|---|
| クリニックスタッフ | クリニックサイト | 商品登録、発注、入荷登録、患者への割当（在庫消費） |
| 法人/グループ管理者 | クリニックサイト | 傘下クリニックの横断管理（範囲は未確定） |
| 卸業者担当者 | 卸ポータル | 自社商品マスタ管理、担当クリニックの発注状況・在庫状況閲覧、自動発注の確認 |

利用者が所属する組織は次の階層になる。

```
法人（Corporation）
└─ グループ（Group）      … 法人内でのグループ化
    └─ クリニック（Facility） … 医科／歯科／獣医
```

## 業務フロー

1. 卸業者を発注先として登録する
2. 卸業者ごとの商品マスタ（卸商品）を登録する（ベンダー名、卸商品コードを含む）
3. クリニックは卸商品を元にクリニック商品を登録し、クリニック独自の商品コードを割り当てる。あわせて発注点を設定する
4. 在庫が発注点を下回った場合、アラート通知 or 自動発注（クリニックの設定による）
5. 発注確定 → 発注書を発行する
   - a. スタッフが発注書をもとに卸の購買サイトへ手入力する運用
   - b. EDIでデータを卸の購買システムへ連携する運用
6. 卸ポータル側では、担当する複数クリニックの発注状況・在庫状況・自動発注の内容を確認できる
7. 発注品が到着したら入荷登録を行う。対象商品はクリニック商品として登録済みであることが前提。ロット番号・使用期限を入力する（入力の簡略化が課題）
8. 入荷登録により在庫が加算される
9. 患者への処方・使用時、バーコード（JANを基本、JANがない商品は名称等で検索）をスキャンし、該当商品を確定して在庫を減算する

## 権限

MVPでは細かく作り込まず、まず一連の業務フローを通すことを優先し、権限は2段階から始める。

| ロール | 操作範囲 |
|---|---|
| クリニックスタッフ | 自クリニックのみ（商品登録・発注・入荷・在庫消費） |
| 法人管理者 | 配下の全クリニックを閲覧・操作可能 |
| グループ管理者 | 後回し。MVPでは法人管理者に統合し、グループ単位の権限分割は後続で切り出す |
| 卸業者担当者 | 契約している複数クリニックの発注状況・在庫状況を閲覧のみ（操作不可） |

認証・認可をどう実現しているか（Auth0の設定、ロールと所属クリニックの持たせ方、卸ポータルの認証）は[architecture/authentication.md](architecture/authentication.md)にある。

## 会計との境界

在庫評価には納入単価が要り、納入単価は会計と地続きになる。どこまでを在庫システムが持ち、どこから会計ソフトの領域なのかを決めないと、値引き・リベート・送料・消費税といった金額項目の置き場所が決まらない。この章はその線引きを定める。

```
発注確定    → 債務は発生しない（発注残）
入荷・検収  → 買掛金が発生する        ★ このシステムが持つのはここまで
月次請求書  → 納品書との突合
支払        → 会計ソフト
```

このシステムは**仕訳を作らない**。作るのは「入荷実績 = いつ・どの卸から・何を・何個・いくらで受け取ったか」で、これがそのまま買掛計上の元データになる。会計ソフトへは入荷明細として渡す。

判断基準は次の1点。

> **その金額を、モノ1個に貼り付けられるか。**

貼り付けられるなら在庫システム、期間や取引先に紐づくなら会計ソフト。

| 金額項目 | モノに貼れるか | 領域 | 理由 |
|---|---|---|---|
| 納入単価 | 貼れる | 在庫 | ロットの取得原価そのもの |
| 明細単位の値引き | 単価に溶ける | 在庫 | 値引き後の単価が納入単価になる。「値引き」という概念を持つ必要が無い |
| リベート（仕入割戻） | 貼れない | 会計 | 期間の購入実績で後から決まり、どのロットにも配賦できない |
| 早期支払割引（仕入割引） | 貼れない | 会計 | 支払条件による割引で金融取引の性格。仕入原価とは無関係（営業外収益） |
| 送料・配送料 | 按分が要る | 会計 | 1回の配送に複数商品が乗るため明細に貼れない。棚卸資産の取得価額は「購入代価＋付随費用」だが、少額なら費用処理する扱いが一般的で、在庫原価には含めない |
| 消費税 | 貼れるが用途が違う | 両方 | 在庫は税抜で評価し、税は買掛の計上時に扱う |

この線引きから、在庫評価と消費税の持ち方が次のように決まる。

- **在庫評価**: Lotが納入単価（税抜）を原価として持ち、在庫金額は`Σ(ロット残数 × ロット原価)`で算出する。評価方法（移動平均法・最終仕入原価法など）はシステムで1つに固定しない
- **消費税**: 単価は税抜で持ち、税率をフィールドとして持つ。税込は計算で出す。卸の請求書との突合では、自分で計算した税額ではなく請求書に記載された税額を正とする

それぞれの理由（リベートを扱えない理由、ロット原価で持つと評価方法を選び直せる理由、インボイスの端数処理、クリニックの控除対象外消費税など）は[accounting-boundary.md](accounting-boundary.md)にある。

## 未確定事項

- グループは必須の中間概念か、法人配下に直接クリニックがぶら下がるケースもあるか
- 在庫・発注はクリニック単位で完結するか、グループ/法人で集約在庫を持つ運用もあるか
- ロット/使用期限管理の入荷UI簡略化の具体案（バーコードにロット/期限が含まれるGS1データバー等の活用可否）
- JANなし商品の名寄せ・検索方法（表記ゆれ対策、候補選択UI）
- 自動発注の確定条件（承認フローの要否、卸側での自動受注可否）
- EDIの卸ごとのフォーマット調査（対象卸を先に確定する必要あり）
- グループ単位での細かい権限分割（MVP後）
- **廃盤になった卸商品の発注をどう扱うか**
  - 現状、廃盤チェックはクリニック商品の**登録時のみ**（`RegisterClinicProductUseCase`）。登録後に卸が廃盤にした商品は、カート追加・発注確定のどちらでも検証されず**そのまま発注できる**。クリニック商品一覧・発注画面にも廃盤の表示が無い。
  - 商品マスタCSVの取り込みで`discontinued`が自動更新されるようになったため、「昨日まで発注できた商品が今日から廃盤」という状態が実際に発生する（別リポジトリ`clinic-inventory-csv-functions`の`docs/catalog-import-backend.md`）。
  - 論点は止める場所と強さ。案は (A) 発注確定時にブロック（卸へCSVを送る直前が最終防衛線） / (B) カート追加時にブロック / (C) 画面に廃盤表示だけ出して止めない。廃盤でも在庫を持つ卸や後継品案内待ちがあるため、どこまで硬く止めるかは卸の運用確認が必要。
  - 「発注はできたが卸に在庫が無い」ケースは別問題で、未実装の受注確定CSV（欠品数量）で埋まる。
- **契約（クリニック×卸業者）が未実装で、取引の無い卸・商品まで選べる**
  - [決定事項](#決定事項)で「契約はクリニック×卸業者の単位」と決めているが、契約を表すデータも画面も無い。そのため商品マスタ画面の卸業者プルダウンには全卸が並び、卸商品一覧も契約の有無に関係なく全商品が出る（取引の無い医院では医院別単価が無いので0円になる）。
  - 同じ契約情報は卸ポータルの閲覧範囲（自社と契約しているクリニックのみ）にも必要で、そちらも現状は絞り込めていない。
  - 論点は、契約を持つテーブルを作って絞り込むか、当面は運用でカバーするか。医院別単価の有無で「その医院が扱う商品」を代用する案は、単価を公表しない卸では区別が付かないため採らない。
  - 上の「廃盤になった卸商品の発注」と同じく、**選べてはいけないものが選べる**という系統の穴。
- **会計ソフトへ渡す形が未定**
  - [会計との境界](#会計との境界)で「入荷実績までを出し、仕訳は作らない」と線を引いたが、渡す形（月次の入荷明細CSVか、会計ソフト個別のインポート形式か）は決まっていない。クリニックが既に使っている会計ソフトがあれば、それに合わせる必要がある。
- **税率をいつスキーマに持たせるか**
  - 現在は税抜単価のみで税率のフィールドが無い（[決定事項](#決定事項)の2026-07-20決定）。在庫評価だけなら税抜のままで足りるが、買掛の元データを出す段階で税率が要る。持ち方の方針は[会計との境界](#会計との境界)で決まっているが、導入時期は未定。
- **納入単価がどの形で届くか卸に未確認**
  - 在庫のロット原価をそのまま埋められるかが、受注確定CSVの列の作りで変わる。(a) 値引き後の納入単価が1列で来るか、単価と値引額が別列か（後者だと在庫側で減算が必要になる）、(b) 税抜単価が来るか税込単価しか来ないか（後者だと割り戻しが必要で端数が問題になる）、(c) 送料が別建てで来るか。詳細は`clinic-inventory-csv-functions`の`docs/order-acknowledgement-import.md`。

| 2026-07-20 | 発注番号の採番 | MVP第一歩ではID(UUID)のみで発注を管理し、クリニックごとの連番採番は後続とする。連番は発注書PDF生成ステップで導入する | 連番採番は並行発注時の重複回避（採番ロック等）の設計が必要で、発注の作成・確定という中心フローを先に通すことを優先したため |

## 用語集

| 用語 | 意味 |
|---|---|
| 卸業者（Distributor） | 医薬品の発注先。会社ごとに約5,000点の商品を扱う |
| 卸商品マスタ | 卸が持つ商品マスタ。ベンダー（メーカー）名、卸独自の商品コードを保持 |
| クリニック商品マスタ | クリニックが卸商品を元に登録する商品。クリニック独自の商品コードを付与 |
| ロット（Lot） | 入荷時に記録する製造ロット番号 |
| 使用期限 | ロットごとの有効期限 |
| 発注点 | 在庫がこの数量を下回ったら発注が必要になる閾値 |
| EDI | クリニックの発注データを卸の購買システムへ電子的に連携する仕組み |
